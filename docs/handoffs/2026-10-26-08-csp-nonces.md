## 3. How it works

1. **The proxy** (`frontend/proxy.ts`) runs before each page request. It makes 16 random bytes with `crypto.getRandomValues` and encodes them as 24 base64 characters. That is 128 bits, so guessing is hopeless.
2. It puts the policy containing `'nonce-<value>'` on the **request** header `Content-Security-Policy`, which only Next.js sees. Next.js reads the nonce from there and adds `nonce="<value>"` to every `<script>` it writes: framework code, page chunks and its inline page data. The proxy overwrites any CSP header the caller sent, so a visitor cannot choose the nonce for their own page.
3. It sends the policy to the browser on the **response**, in Report-Only mode for now.
4. **Every page renders per request** (`await connection()` in the root layout), so every response gets a fresh nonce.
5. The proxy skips `/api/…`, `/auth/…`, `/health`, built files under `/_next/`, `/favicon.ico`, link prefetches, and **`/python-worker.js`**. The worker keeps its own enforced policy from `next.config.mjs`, unchanged: Pyodide only from `cdn.jsdelivr.net`.

### The policy, and what changed from handoff 06

```text
default-src 'self'; script-src 'self' 'nonce-<new every request>'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'
```

- **Only change:** `script-src 'self' 'unsafe-inline'` became `script-src 'self' 'nonce-…'`. Everything else is exactly handoff 06's policy.
- **No `'strict-dynamic'`.** The Next.js guide adds it, but it makes the browser ignore `'self'` and trust any script that a trusted script inserts. We don't need it: every script Next.js loads later is a file from our own site, which `'self'` already allows. I tested without it (section 7). Leaving it out keeps the policy narrower.
- **Report-Only, next to the old policy.** One Next.js detail matters here: when the proxy sets `Content-Security-Policy-Report-Only`, it **replaces** the same header from `next.config.mjs` rather than adding to it. So the proxy now sends both policies in one header, separated by a comma, which browsers treat as two separate policies. The old one allows inline scripts, so it never reports anything the new one does not. It stays until you switch.

## 4. What I found while building it

- **Next.js's built-in 404 page breaks `style-src 'self'`.** It has an inline `<style>` tag and `style="…"` attributes with no nonce, under both handoff 06's policy and the new one. Handoff 06 never visited a missing page, so this was missed. With the policy enforced, the 404 page would have shown up unstyled. I added `app/not-found.tsx`: a heading, one sentence and a link home, using the app's own stylesheet. It is the only visible change.
- **`next dev` cannot run under a strict policy.** The development server puts styles in inline `<style>` tags and uses `eval`, and the old policy already reported both in development. So `next dev` always stays Report-Only, even after you set `ENFORCE = true`. Production builds (`npm run build`, Render, CI) do not need either.
- **Static rendering and nonces cannot be combined.** A static page is written once at build time, when there is no request and so no nonce. I tested this: with the pages left static, 26 of 30 tests fail. That is why every page now renders per request.

## 5. Switching to enforce mode (one line)

In `frontend/proxy.ts`, change:

```ts
const ENFORCE = false;
```

to:

```ts
const ENFORCE = true;
```

Pages then send this instead of the Report-Only header:

```text
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-<new every request>'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; worker-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'
```

**Tested locally, the same way as handoff 06:** I made exactly that change and rebuilt.
- All 30 Playwright tests passed.
- Against the real local API, with no mocks, a browser opened `/`, `/courses`, `/courses/py`, `/learn/hello` and a missing page, each with the enforced nonce policy.
- On `/preview` it ran real Python (`A forest.\nA dragon!\n`), the real `/api/check` returned `passed`, and the Story spark badge appeared. There were no violations.
- I then set it back to `false`.

Enforcing this policy also completes SEC-04, because it replaces handoff 06's enforce step.

## 6. Cost: pages lose static caching

| Page | Before | After |
| --- | --- | --- |
| `/` (home and welcome) | Static: built once, served from Next.js's cache | Rendered per request |
| `/courses` | Static | Rendered per request |
| `/preview` | Static | Rendered per request |
| 404 page | Static | Rendered per request |
| `/courses/<course>`, `/learn/<lesson>` | Already rendered per request | Unchanged, plus the proxy |
| `/api/…`, `/auth/…`, `/python-worker.js`, `/_next/static/…` | — | Unchanged; the proxy does not run on them |

**Caches lost:**
- **Next.js's in-memory HTML cache** on our own Render instance. The live site shows `x-nextjs-cache: HIT` today.
- **Shared caches:** pages used to send `Cache-Control: s-maxage=31536000`; they now send `private, no-cache, no-store`. That is required, because a cached page would hand everyone the same nonce, and a test checks for it.
- **Cloudflare:** nothing lost. Live responses show `cf-cache-status: DYNAMIC`, so Cloudflare was not caching our pages anyway.
- **Browsers:** some don't keep `no-store` pages in the back/forward cache, so the back button may reload the page instead of restoring it instantly.

**Measured locally** (production build, 400 requests, 10 at a time, Apple M5 Pro):

| Page | Before | After |
| --- | --- | --- |
| `/courses` (was static) | 0.56 s (about 710 pages/s) | 0.76 s (about 525 pages/s): about 0.5 ms more CPU per page |
| `/learn/hello` (already per request) | 0.63 s | 0.71 s: the proxy adds about 0.2 ms |
| Page size | 5,724 bytes | 6,105 bytes (the nonce attributes) |
| Server memory after the test | 300 MB | 357 MB |

**On our Render plan:**
- **Money:** the frontend is a Starter web service at a flat USD 7 a month (0.5 CPU, 512 MB). Render does not bill per request, so per-request rendering costs **nothing extra**. Bandwidth grows by about 400 bytes per page view.
- **CPU:** Render's half-CPU is slower than this Mac, so expect a few milliseconds per page view rather than 0.5 ms. That is an estimate, not a measurement. For a handful of testers it is far below what the instance can do.
- **Memory is the one thing to watch.** Locally the server used about 57 MB more after load, and Starter has 512 MB. Memory on a Mac is not the same as on Render, so section 10 asks you to read the frontend's Memory graph. If it ever gets close to 512 MB, the next plan up costs more. I would come back to you before suggesting that.

**Smallest safe alternative, if this ever becomes a problem:** Next.js has an experimental hash-based option (Subresource Integrity) that keeps pages static. It is marked experimental, and it covers script files, not Next.js's changing inline page data, so it would not remove `'unsafe-inline'` by itself. I do not recommend it now. The nonce approach is the one Next.js documents, and it is not fragile here: three small files, no new dependencies, and a test fails if pages go static again.
