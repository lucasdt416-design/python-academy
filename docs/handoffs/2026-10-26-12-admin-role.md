## 3. Decisions and why

The design defaults were decided by the owner in the task. The choices made while building them:

| Decision | Options considered | Reason |
| --- | --- | --- |
| Decide admin **at sign-in**, from Google's answer, and store it on the session row; re-check `ADMIN_EMAILS` on every request | Compare the stored account email with the list on each request; store an admin flag on the user | Only Google's answer at sign-in proves the email is verified *now*. The stored email is from account creation. Re-checking the list means removing an email ends access at once. Nothing in the cookie says "admin" |
| Treat `email_verified` as verified only if it is exactly `true` | Any truthy value | A string `"true"` passes the existing sign-in check, but is not Google's verified flag (tested) |
| Admin is separate from the account role (an admin can be a parent account) | An "admin" role | Roles control family features; the owner's account is a parent. No endpoint can make anyone admin |
| A tester flag only on student accounts; an admin counts as a tester | Testers of any role | Decision 23 |
| Admin actions recorded in the **admin's own** account history as `tester_set` or `tester_cleared` with `user <id>` | Writing the email; writing to the student's history | The owner's default: by user ID, never by email |
| API only, no admin page | A minimal page | Allowed by the task, and the smallest attack surface. The owner uses two `curl` or console commands (section 9) |
| Admin routes are added to the app directly, each with the guard, not through an `APIRouter` | An included router with one shared guard | **Found while building** (section 4): this FastAPI version hides included routers from the route lists that the safety tests read. A test now checks every `/api/admin` route has the guard |
| `ADMIN_EMAILS` documented in `render.yaml` with `sync: false` | Not listing it; putting a value there | Shows it is needed, without ever committing it; the Blueprint never overwrites the dashboard value |
| A rate limit on the admin write route | No limit | The existing rule, "every write route has a limit", is tested |
| Migration 0007: two boolean columns, `NOT NULL` with a server default of false | Nullable columns | The old app version keeps working during the deploy, every existing row gets `false`, and the downgrade removes them cleanly (tested on SQLite and PostgreSQL) |
| `admin` import on its own line in `main.py` | On the same line as the other imports | PR #17 changes that line; the change keeps both PRs mergeable (checked) |

## 4. Bugs found and how they were fixed

- **Near-miss: included routers are invisible to our safety tests.** The first version put the admin routes in an `APIRouter`, included with `app.include_router`. All existing tests passed, which was suspicious: the route-list test should have failed on two unlisted routes.
  - Investigating showed FastAPI 0.162 keeps an included router as one opaque `_IncludedRouter` entry in `app.routes`.
  - So the route-list test (sessions), "every write route has a limit" (rate limits) and PR #17's leak scan **would all have silently skipped every admin route**.
  - Fix: register the routes on the app, each with `require_admin`. New test: `test_no_route_is_hidden_from_these_checks` fails if any route type other than a plain route appears in `app.routes`. Found by: noticing a test that should have failed did not.
- **Noted, not changed: malformed JSON is answered before the guard.** A request with unparseable JSON gets `422` before `require_admin` runs, because FastAPI parses the body first. It reveals nothing (no data, no admin status). Well-formed requests from non-admins always get 403 (tested). Found by a slip in my local `curl` script.

| Every admin route has the guard | Structural check of each route's dependencies |
| Admin session lifetimes (fake clock) | Used every 30 minutes, still refused at exactly 8 hours; refused after 1 hour unused; learner sessions still last past 23 hours |
| Tester flag | The admin sets and clears it; non-students get 422; unknown IDs 404; history rows hold the admin's ID and `user <id>`, no email; **a student cannot set their own flag (403, flag unchanged)**; a tester student sees `tester: true`, `admin: false` |
