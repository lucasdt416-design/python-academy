## 3. Decisions and why

The design document makes **proposals**; the owner makes the decisions (section 10 of the design). The choices made in writing it:

| Decision | Options considered | Reason |
| --- | --- | --- |
| Suggest concept B (code and picture side by side) as the default | A: Lantern Path; C: The Map | B shows the real product honestly (it *is* unit 1), teaches while it markets (predict first), and needs the least art. C's map is folded into B's mission scene to show growth beyond Python |
| Recommend hand-written SVG illustrations | Commissioned art; AI-generated art | Free; matches the art already in the product; tiny files; each part can move; reviewable as code; clear ownership. AI images are hard to keep consistent, cannot be animated in parts, and have unsettled rights; commissioned art costs money (free-first rule) |
| CSS scroll-driven animations first, with no library | Motion, GSAP, Lottie, smooth-scroll libraries, 3D | Nothing to download, nothing to break the policy. Lottie's full player has used `eval`; smooth scrolling takes over the wheel; 3D is too heavy for school laptops |
| A rule: no `style` attributes in server-rendered HTML | Allowing them | Our page policy is `style-src 'self'`, which blocks inline style attributes, and a nonce cannot allow them. Some React animation helpers write starting positions that way |
| Recommend a separate static site | Story inside the app at `/` | No extra cost; landing traffic cannot slow learners; nothing to attack (no cookies or API); fastest first load; **no changes** to sign-in redirects or invitation links. Cost: a second small deploy |
| A short intro instead of a loading screen | A full loading screen, as on the inspiration site | A screen that hides content hurts speed and accessibility. The intro plays over content that is already there and is skipped under reduced motion (question 6) |
| Budgets taken from Google's "good" Core Web Vitals (LCP 2.5 s, INP 200 ms, CLS 0.1), on a throttled profile | No budget | A school Chromebook is slow, so a concrete target lets each later PR be measured |
| Primary call to action: "Try the first lesson, no account needed" (`/preview?lesson=hello`) | "Sign up" first | It already exists, saves nothing, and lets a beginner feel success before any account |
| Do not copy hackcanada.org | — | The owner's instruction; the concepts are built only from our unit 1 world |
| Do not edit `docs/plan/backlog.md`; put the `build.md` row in a different place from PR #18's | Editing both | Avoids merge conflicts with open PRs (checked, section 6) |

## 4. Bugs found and how they were fixed

None: no code changed. Two findings recorded in the design, for later stages:

- **About 70 hard-coded colours** in `frontend/app/style.css`, many of them near-duplicate greens. Not a bug, but it makes consistent polish hard. SITE-03 stage 5 replaces them with about a dozen named colours.
- **A trap for later:** server-rendered `style="…"` attributes would be reported by today's Report-Only page policy and blocked once it is enforced. Recorded as a rule in design section 4.1, so the story and SITE-03 do not run into it.
